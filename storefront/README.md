# متجر «الأصيل» الإلكتروني

واجهة عرض وطلب للزبائن — قمصان وأقمصة رجالية محتشمة. React 18 + Vite +
Tailwind، تقرأ `publicCatalog` مباشرةً من Firestore بلا خادم وسيط وبلا
تسجيل دخول.

## التهيئة

معرّف المتجر (uid صاحب المحل) يُمرَّر كمتغيّر بيئة:

```bash
cp .env.example .env.local
```

ثم ضع فيه `VITE_STORE_ID`.

تجده في لوحة Firebase → Authentication → UID الخاص بحساب صاحب المحل،
أو في مستند `user_store_map/{uid}` تحت الحقل `storeId`.

## التشغيل والبناء

```bash
npm install
```

```bash
npm run dev
```

```bash
npm run build
```

## النشر على Vercel

استورد المستودع في Vercel واترك **Root Directory** على جذر المستودع كما هو.
ملف `vercel.json` في الجذر يتكفّل بالباقي:

```json
"installCommand": "npm install --prefix storefront",
"buildCommand":   "npm run build --prefix storefront",
"outputDirectory": "storefront/dist"
```

لماذا في الجذر لا في `storefront/`؟ لأن المستودع مشروع Flutter وجذره ليس
مشروع Node؛ بلا هذا الملف يفتّش Vercel عن `package.json` في الجذر فلا
يجده ويفشل البناء. (يبقى `storefront/vercel.json` صالحاً لمن يفضّل ضبط
Root Directory يدوياً على `storefront`.)

**الخطوة الوحيدة اليدوية**: أضف متغيّر البيئة

| المفتاح | القيمة |
|---|---|
| `VITE_STORE_ID` | uid صاحب المحل |

في Vercel ← Settings ← Environment Variables، ثم **Redeploy**. بدونه يُبنى
الموقع وينشر ويفتح، لكنه يعرض «المتجر غير مهيّأ» بدل المنتجات — لأن Vite
يخبز القيمة وقت البناء لا وقت التشغيل.

الـ rewrite في `vercel.json` يُرجع كل المسارات إلى `index.html` (تطبيق صفحة
واحدة، وبدونه تُعطي إعادة تحميل أي مسار خطأ 404).

## الهوية تأتي من التطبيق لا من الكود

اسم المحل، الجملة التعريفية، الهاتف، ورابطا فيسبوك وإنستغرام تُقرأ من
`publicCatalog/{storeId}/meta/storefront` — ينشرها التطبيق من شاشة
الإعدادات. فيغيّر صاحب المحل رابط صفحته من هاتفه ويظهر في الموقع فوراً
**بلا إعادة بناء ولا نشر**.

غياب المستند ليس خطأ: تظهر القيم الافتراضية (الاسم «الأصيل») حتى يُحفظ
أوّل مرّة.

- أزرار فيسبوك/إنستغرام تظهر فقط إن ضُبطت روابطها.
- رموز QR في التذييل مخفيّة على الهاتف عمداً (`hidden sm:flex`): من يتصفّح
  بهاتفه لا يستطيع مسح رمز معروض على الهاتف نفسه، والزرّ فوقه يكفيه.
- الشعار `public/logo.png` و`public/favicon.png` يولّدهما
  `dart run tool/generate_icons.dart` من `assets/images/logo.png` في
  التطبيق — مصدر واحد لا نسختان تتباعدان.

## ما يراه الزائر وما لا يراه

الزائر يقرأ `publicCatalog/{storeId}/products` فقط — وهي مرآة لا تحوي
**سعر الشراء ولا المورّد ولا الباركود ولا الكميات**، بل `inStock` منطقياً
فقط. ويقرأ مستند الهوية أعلاه — وهو أيضاً قائمة بيضاء لا تحوي تجزئة الرقم
السرّي ولا أي إعداد داخلي. مجموعة `stores/**` مغلقة تماماً على غير
المصادَقين.

## رقم الطلب

عدّاد في `publicOrders/{storeId}/meta/counter` يُزاد بمعاملة ذرّية.
القواعد تسمح بزيادة **واحدة فقط** في كل تحديث (`value <= resource.value + 1`)،
فلا يستطيع زائر القفز بالعدّاد ولا تخريبه. الصيغة `KM-2026-001`،
وتعود إلى 1 مع بداية كل سنة.

## بنية الطلب

مقيَّدة بدالة `isValidOrder` في `../firestore.rules`: مفاتيح محدّدة لا غير،
`status: 'pending'` إجبارياً، حدود على أطوال الاسم والهاتف والولاية
والملاحظة، وعلى عدد المنتجات (≤50) وعلى الإجمالي. التحقّق في
`CheckoutForm.jsx` يطابق هذه الحدود حرفياً حتى تظهر رسالة عربية واضحة
للزبون بدل رفض غامض من الخادم.

الطلب يصل إلى قسم «الطلبات» في تطبيق المحل، حيث يمرّ بـ:
`جديد → مؤكَّد (يحجز الكمية) → مُرسَل (يُنقص المخزون) → مُسلَّم`.
